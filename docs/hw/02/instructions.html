Image Format

Some background on how user modules are stored in the system image would be helpful context.

Thus far, we have been storing the kernel in minemu’s System ROM as part of a single image, as we have not yet covered how things ought to be organized in a disk file system yet.

Currently, the system image packages the kernel together with independently compiled and linked user modules. After the bootloader starts the kernel, it passes a minemu_boot_info struct that describes where the image itself is located and where its module table can be found.

The module table is an array of module records, each of which corresponds to a user program present in the image. The record holds metadata like the program name, entry address and the program’s segment table.

The segment table holds segment records, which describe:

  • where the program’s code and data are stored in the image
  • where they should appear in virtual memory
  • how much memory they require
  • whether they should be readable, writable, or executable

To load a user program, the kernel:

  1. searches the module table for the requested name
  2. selects physical RAM pages for its segments
  3. copies the initialized bytes from the image
  4. zeros any remaining uninitialized data such as BSS
  5. creates a separate writable, non-executable user stack

After the program and stack have been mapped, the kernel can enter user mode at the module’s entry address with the user stack pointer active.

MMU and Virtual Memory

We will cover the Memory Management Unit (MMU) and Virtual Memory in greater depth in Unit 3 of the course, but virtual memory is a core concept for implementing processes and user space, so we will need to discuss it now.

Virtual memory allows a program to use virtual addresses without directly controlling the physical RAM or device addresses behind them. The kernel builds page tables that translate each virtual page into a physical page and attach permissions describing whether that page may be read, written, executed, or accessed from user mode.

The kernel creates a new virtual address space by creating new mappings of virtual pages to physical pages in a page table. When switching between processes, the kernel will be able to swap out the current page table with the new one, allowing the new translation mapping to take effect.

For this assignment, the kernel gives the user program access to its own code, data, and stack while keeping kernel memory and MMIO device registers supervisor-only. This separation is what prevents user code from bypassing the syscall interface and directly controlling hardware.

The ARM architecture defines a special hardware module called Coprocessor 15 (CP15) as a control and status interface for CPU functionality. CP15 registers can be accessed via the special mcr/mrc instructions and are used among other things to configure and enable the MMU.

The user-mode-hello example shows how the kernel first maps the user modules in System ROM into the kernel’s address space to make them readable, then how the kernel can create a new address space for a user program, and copy the program into that space.

Part 1: Implementing a Syscall

As we learned in class, a system call (syscall) is a controlled way for an unprivileged program to ask the kernel to perform an operation on its behalf.

In this assignment, you will be implementing the ioctl (I/O control) syscall, which will be designed to allow user code to interface with some of minemu’s peripherals.

Syscall Path

In ARM, a syscall is made by invoking the instruction SVC =0 and passing the arguments via registers r0-r7. By convention, the syscall number is passed to the kernel in register r7, and other parameters in r0-r6.

After the processor switches to pivileged mode, it saves the previous processor status in SPSR_svc, stores a return address in LR_svc, and jumps through the SVC entry in the exception vector table.

The SVC vector branches to an assembly trampoline, which saves the interrupted register state in an SVC frame and passes it to the C syscall dispatcher. The dispatcher verifies that the exception came from A32 user mode through the expected svc =0 instruction, checks the syscall number and request, validates any user-memory ranges, and performs the operation. It writes the syscall result into the saved copy of r0. The trampoline then restores the saved state and returns to the instruction after svc, allowing the user program to continue with the return value in r0.

SVC Frames

An SVC frame is the kernel’s in-memory record of the user program at the moment it requested a syscall.

For now, the frame is 88 bytes and stores the following:

  • r0-r12
  • the exception return address
  • the saved CPSR
  • the exception identifier
  • fault information
  • the user-mode stack pointer
  • the user-mode link register

Some of these values must be saved explicitly because ARM uses banked stack and link registers for different processor modes.

For an SVC exception, LR_svc points to the instruction after svc, so the trampoline records LR_svc - 4 as the address of the SVC instruction itself. The dispatcher changes the saved r0 when it wants to return a result, and the assembly code restores the rest of the frame before returning.

Saving the interrupted state in one well-defined structure makes syscall handling easier to reason about and also establishes the basic context representation that later assignments can reuse for scheduling and context switching.

ioctl System Call

We would like to use ioctl to enable user access to the UART, RNG, and TRACE peripherals, as MMIO register operations are only possible in privileged mode. int ioctl(int fd, int op, ...) is a UNIX system call that is used to interface directly with kernel drivers when other system calls like read, write and open aren’t suitable.

The ioctl function is designed to be flexible. The fd (file descriptor) argument in r0 is used select the device (everything is a file in UNIX), while the op argument in r1 is a device-specific operation identifier. There are up to 2 additional variadic arguments that can be provided in r2 and r3, depending on the device being accessed.

The ioctl syscall number (and all syscall numbers) should be defined in a C header file shared in both user and kernel programs.

The fd value should accept values for UART0, UART1, RNG, and TRACE peripherals, and op values should be defined for the following behavior:

fdopVariadic ParamsDescription
0x10003000 (RNG)0x0 (rng_set_seed)unsigned int seedrng_set_seed should be used to update the RNG seed register. It returns 0 on success.
0x10003000 (RNG)0x1 (rng_get_data)unsigned int * datarng_get_data should store a random value in the data output pointer. It returns 0 on success.
0x10004000 (UART0)0x0 (uart_read)char * dst, int nuart_read reads all data available, up to n bytes and stores it in the dst buffer. It returns the number of bytes read, or a negative value on failure.
0x10004000 (UART0)0x1 (uart_write)char * src, int nuart_write writes n bytes of data from src to the UART device. It returns the number of bytes written, or a negative value on failure.
0x10005000 (UART1)0x0 (uart_read)char * dst, int n(same as above, but for UART1)
0x10005000 (UART1)0x1 (uart_write)char * src, int n(same as above, but for UART1)
0x1000f000 (TRACE)0x0 (trace_event)unsigned int valuetrace_event generates a hardware trace event with the given value. It returns 0 on success.

ioctl should also return a negative value if it detects invalid values for fd or op.

Because syscall arguments can include user-provided pointers, the kernel must treat them as untrusted. It validates every page in a requested range before reading user data, writing into user memory, removing UART input, advancing the RNG, or producing any other visible effect.

Part 2: Move msh to User Mode

Now that we have a syscall that will let us print to the console from user-mode, we can make the msh shell from homework 1 into a user-mode program.

The msh shell has all of the same expected behavior as before:

  • Print the prompt msh> whenever ready for a command
  • Ignore ASCII spaces before a command

  • Use only the newline character \n as a line terminator

    • Lines can be up to 20 bytes long
    • Overlong input must be accounted for

  • Handle backspaces correctly

    • Treat both 0x08 and 0x7f as backspace
    • Ignore backspace on an empty line
  • Treat an empty or all-space line as an empty command and return to prompt

  • Recognize the echo command:

    • echo TEXT prints TEXT followed by a newline \n
    • echo without text prints an empty line
    • Treat repeated spaces after echo as a single separator
  • Respond to an unknown, non-empty command with command not found: COMMAND, followed by a newline, where COMMAND is the first ASCII space-delimited word.
